# SR Update

For unknown capabilities or a bundled unavailable/unsupported claim, follow
[Live Capability And Version Check](../sr-plugin/SKILL.md#live-capability-and-version-check)
first. The authenticated live catalog supersedes bundled capability lists;
returned authorization and confirmation policies still apply.


Lead with the current outcome, not a history dump. Read [Update Composition](references/update-composition.md)
before combining more than one source.
Apply [Response And Channel Policy](../sr-plugin/references/response-and-channel-policy.md)
for channel timing, audience authorization, private continuation, and the
single natural terminal answer.

## Build The Update

1. Determine the requested scope and time horizon from the conversation.
2. Reuse established refs and facts, then refresh only drift-prone facts needed
   for the update.
3. Use SR Data for Product facts or runtime health. Use SR Coordination for
   participant-visible messages, conversations, and Admin priority cards only when
   each requested capability is visibly available on the authenticated
   backend.
4. Separate verified current state, material changes, open blockers, and the
   next useful action.
5. State coverage gaps explicitly. A Product-only update does not cover the
   personal message Inbox or Admin priority board.

Do not mutate state, acknowledge messages, complete priority cards, or prepare Product
actions merely because an update surfaced them. Route a requested follow-up to
the owning skill.
