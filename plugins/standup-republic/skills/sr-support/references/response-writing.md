# Support Response Writing

Use this reference when the user asks for an answer to a colleague, comedian,
promoter, venue, or organizer.

## Internal Diagnosis

Structure the internal result as:

1. direct answer or diagnosis;
2. verified facts that establish it;
3. material unknowns or freshness;
4. smallest useful next step;
5. action preview and confirmation state, when applicable.

Do not bury the answer under the investigation process. Do not expose internal
tool names or refs unless they are needed for audit or disambiguation.

## External Draft

Keep the draft separate from internal notes. The draft should:

- answer the person's actual question first;
- use natural language and only recipient-relevant facts;
- avoid internal identifiers, private notes, unrelated people, access details,
  finance data, and speculative root causes;
- distinguish what is already true from what still needs action;
- avoid claiming that an action, payout, booking, or message occurred without
  verified evidence;
- give one clear next step when the issue is unresolved.

## State Patterns

- **Answered:** “Aktuell ist …” followed by the verified fact.
- **Needs clarification:** ask for one missing date, city, account, or event
  discriminator.
- **Needs confirmation:** only when Execute is enabled, state the exact proposed
  change, that nothing has run, and request confirmation of one manifest. When
  Execute is disabled, label the preview `blocked` and do not request approval.
- **Denied or unsupported:** explain the boundary without suggesting a bypass.
- **Possible incident:** state what is affected and verified; do not invent a
  root cause or recovery time.

Never say or imply that the draft was sent.
